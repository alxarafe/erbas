# API internationalization

The runtime supports English (`en`) and Spanish (`es`). English is the base and
fallback. `LocalizationConfiguration` installs Spring MVC's stateless
`AcceptHeaderLocaleResolver` with those supported neutral locales and an explicit
English default. Standard header negotiation handles regional variants such as
`es-ES` and `en-US` and quality preferences. Missing or unsupported languages use
English. Query parameters and cookies do not select the locale.

## Resource ownership and composition

Core's transversal messages live in `erbas-core/src/main/resources/i18n/core/messages.properties`
and `messages_es.properties`. The unsuffixed bundle is English. Spring Boot
configures its native `MessageSource` through `spring.messages.basename`; system
locale fallback is disabled, so deployment locale cannot change the base language.

Each future module owns and packages its resources with its code, using a distinct
basename, for example `i18n/contact/messages`. The composition root adds known
basenames explicitly to the comma-separated setting. Multiple modules must not
reuse an ambiguous root `messages` basename. There is no bundle discovery system,
translation wrapper, remote catalog or global module message registry.

## Validation and HTTP errors

`spring-boot-starter-validation` enables Jakarta Validation and Spring Boot's
native MessageSource integration. HTTP request DTOs can use `@Valid`, nested
`@Valid` values/collections and constraints with module-owned message keys, such
as `@Size(message = "{contact.validation.name.size}", ...)`. Resource phrases
can interpolate standard constraint attributes such as `{min}` and `{max}`.

`ValidationExceptionHandler` handles only `MethodArgumentNotValidException`.
It returns native Spring `ProblemDetail`, with stable status 400 and
`code: validation_error`, localized transversal title/detail and an `errors`
map. Field paths, including collection indexes, are canonical and unchanged;
object-level errors retain their canonical object name.
It resolves Spring error objects through `MessageSource.getMessage(resolvable,
locale)` rather than prematurely flattening their recursively resolvable arguments.
Domain/Application remain independent of Spring localization and request state.
Future module-specific errors retain module-owned resource keys and HTTP adapters.

Published ERBAS Contract v0.8.0 errors remain closed. AUTH, Users, Modules, WMS and their
security/gating errors use the closed `{code, errors}` envelope. Each detail
requires its technical code and can carry only contractual `resource`,
`resourceId` and JSON Pointer `path` context. The platform's `ContractError`
serializes this shape consistently; WMS owns its association-specific mapping.
No localized message, title, status, timestamp or internal diagnostic is added.
Existing statuses, technical codes and successful responses are preserved.
Health and successful responses likewise remain language independent. Enriching
shared errors would require a separate versioned contract change.

WMS description is stored user content and is never translated. WMS error codes
remain technical and no empty WMS message bundles are registered. Java currently
has no generated production user-facing message or Jakarta-validated business
endpoint. `LocalizationHttpTests` therefore exercises the real MVC negotiation,
MessageSource, validation and ProblemDetail pipeline using controllers and
`i18n/probe` bundles exclusively in `src/test`. Maven does not package these test
classes/resources into the application artifact. No business capability or
production probe endpoint is introduced.

## Verification

The existing complete authority remains:

```bash
ERBAS_CONTRACT_DIR=/absolute/path/to/clean-v0.14.0-checkout ./bin/check
```

HTTP tests cover explicit English/Spanish, missing headers, unsupported French,
regional variants, quality negotiation, request isolation, ignored query/cookie
language selectors, nested stable paths and parameterized constraints. The same
check retains full shared v0.14.0 conformance and disposable PostgreSQL cleanup.

Use complete parameterized resource phrases for all human runtime text. Never
translate routes, schemas, JSON properties, codes, canonical field names, IDs,
permissions or internal diagnostics. Multilingual OpenAPI, stored-content
translation, user language preferences and CONTACT-002 are outside this task.
